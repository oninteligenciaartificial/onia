# Lecturas de servicios desde Codex VPS

8 de noviembre de 2026, America/Caracas. Entrega de análisis; **ningún conector instalado ni acceso activado**. Evidencia y fuentes en [EVIDENCIA](EVIDENCIA.md), aceptación futura en [PRUEBAS](PRUEBAS.md) y responsables en [SIGUIENTES](SIGUIENTES.md).

## Resultado y decisión propuesta

La ruta de menor riesgo y sin compra es un **paquete de lectura preparado por el coordinador con una conexión existente**, validado y entregado como archivo al ejecutor. Resuelve consumo de contexto desde CLI sin trasladar credenciales. Después conviene desarrollar un lector API de alcance fijo y probarlo con datos sintéticos; MCP oficial queda como alternativa para consultas interactivas, donde haya control suficiente de permisos. X queda fuera de lecturas API reales mientras no exista una condición económica verificada compatible con cero gasto.

La lista MCP global está vacía, pero esta sesión anuncia plugins del chat. Son mecanismos diferentes. `--ignore-user-config` omite `$CODEX_HOME/config.toml`, no la autenticación de Codex: agregar MCP al archivo global no resuelve por sí solo los hijos del harness. Tampoco la autenticación ChatGPT autentica automáticamente APIs de terceros. La ayuda local y `harness_sesiones.py:259–282` sustentan este diagnóstico; no se lanzó otro proceso Codex para ensayarlo.

## Tres alternativas completas

### A. MCP oficial por servicio

Flujo: elegir proveedor y versión → comprobar transporte y catálogo → autorización oficial → custodiar credencial → inyectar configuración no secreta en el lanzamiento → listar herramientas → lectura de fixture → guardar recibo mínimo → revocar/retirar acceso cuando corresponda. Cliente Codex admite stdio y Streamable HTTP; una llamada MCP de lectura puede usar POST en el transporte sin ser escritura del servicio. [MCP Codex](https://learn.chatgpt.com/docs/extend/mcp).

GitHub es el candidato más claro por su modo remoto readonly. Notion alojado evita instalación, pero el OAuth del usuario puede editar; su servidor open source ya no es el camino mantenido recomendado. Drive oficial existe en preview y requiere preparación de cuenta que está excluida de este encargo. n8n de instancia mezcla lectura con ejecutar/editar. X no tiene aquí un candidato oficial verificado ni una condición gratuita demostrada.

Ventaja: descubrimiento tipado e interacción con datos actuales. Coste operativo: autenticación por cliente, cambios de catálogo y compatibilidad. Riesgo: servidor o token con capacidad mayor que la expuesta al modelo. Recuperación: fallar cerrado si no inicializa o cambia el catálogo; renovar con custodio, no instalar otro paquete a ciegas. No usar Docker, `npx` sin versión ni servicios persistentes para este análisis. No se descargó ni ejecutó ningún servidor.

### B. Lector de API directa con operaciones fijas

Flujo: seleccionar recurso → custodio obtiene credencial mínima → recolector de una sola ejecución realiza peticiones allowlisted → valida esquema/paginación/tamaño → elimina campos sensibles → entrega paquete y manifiesto → consumidor CLI verifica integridad → retoma por checkpoint de consulta. Empezar con GitHub público sin token permite validar el circuito sin cuentas nuevas; no acredita acceso privado. Para Notion, una integración Read content ofrece mejor restricción de proveedor que un OAuth personal amplio.

Propuesta de implementación posterior: `read(service, resource_alias, cursor)`; no aceptar URL, cabeceras ni método libres. Límites iniciales de diseño: 10 s conexión, 30 s operación, 1 MiB por página y 3 páginas por ejecución; exceder devuelve incompleto y cursor, nunca éxito integral. Validar host HTTPS fijo, no redirecciones, campos permitidos, IDs y tipos. Retries sólo para lectura, hasta dos, respetando Retry-After y presupuesto; 401 admite a lo sumo una renovación, 403 no eleva permiso. Son límites propuestos, sin medición del servicio.

Ventaja: menos superficie, salida estable y pruebas sin producción. Coste: mantener adaptadores y versiones API; no presupone coste monetario cero de todas las APIs. Con credencial amplia accesible al mismo shell, un helper GET-only **no impone** sólo lectura: el agente puede saltarlo. Para n8n amplio, usar prelectura por custodio y entregar sólo datos, o aislamiento efectivo futuro; una variable de entorno y un prompt no bastan.

### C. Paquete/puente coordinado sin credenciales en el hijo

Flujo: coordinador selecciona fuente y lectura autorizada → usa plugin existente con operación precisa → sanea resultado → conserva privado fuera de Git si corresponde → produce manifiesto → entrega ruta y hash al worktree permitido → hijo verifica y analiza → devuelve conclusiones locales, sin capacidad de escribir al proveedor por ese canal. No hay bot, servicio ni sincronización implícita; cada actualización es otra lectura autorizada.

Manifiesto propuesto: versión de esquema, servicio, alias de recurso, fecha de obtención con zona, revisión/ETag si existe, operación, alcance, paginación completa o cursor, tamaño, hash de bytes, productor y caducidad. No incluir tokens, emails, URLs firmadas ni cuerpos de error privados. Hash detecta cambios; confianza/autenticidad exige productor y canal conocidos, no sólo hash.

Ventaja: aprovecha conexiones existentes, no exige key en VPS y funciona con `--ignore-user-config`. Límite: snapshot potencialmente viejo y dependiente del coordinador; no da consulta libre ni prueba API directa. Duplicado con igual recurso/revisión/hash reutiliza paquete; mismo ID y hash distinto bloquea por conflicto. Escritura atómica más checkpoint evita aceptar una exportación cortada. Es la opción inicial recomendada para los cinco servicios, pero n8n/X siguen necesitando una fuente realmente accesible y autorizada; el puente no inventa acceso.

## Primer acceso concreto y custodia

**Propuesto, pendiente de nuevo encargo de ejecución:** el coordinador elige una página Notion sintética ya existente que pueda compartir, hace fetch de esa única página con el conector actual y entrega texto saneado + manifiesto a un ejecutor CLI. No crear página ni leer el panel personal como parte de este análisis. Si no existe fixture, usar un archivo público de GitHub fijado por SHA para el primer paquete; la sustitución prueba transporte, no acceso Notion. Cierre: hash correcto, contenido esperado, alcance/truncación explícitos y petición de actualizar el origen rechazada localmente.

Privados: conservar en almacenamiento privado aprobado del consumidor, con permisos de directorio 0700/archivo 0600 y retención definida; no Git, tampoco sólo `.gitignore` como protección. Los secretos siguen en la conexión administrada del chat. Para API futura, custodio fuera del repo y del entorno legible del agente; registrar etiqueta, consumidor, recurso, permisos, vencimiento, última prueba y revocación, nunca el valor. Keyring puede ser opción OAuth del CLI, pero su disponibilidad en este VPS no se probó; fallback de archivo requiere protección real y revisión, no suposición de cifrado. [Almacén OAuth configurable](https://learn.chatgpt.com/docs/config-file/config-reference).

El sandbox workspace-write no es una ACL de escritura de SaaS. Incluso `--sandbox read-only` no debe confundirse con credencial SaaS read-only. Para rechazo fuerte: credencial mínima del proveedor o datos offline sin esa credencial; controles del cliente son defensa adicional. Datos recuperados se tratan como contenido no confiable: instrucciones incluidas en una página no autorizan otras consultas, envíos ni cambios.

## Integración futura con el harness

Mantener `--ignore-user-config`. Para C no se necesita modificar el lanzador: el encargo referencia un paquete privado disponible y su recibo saneado. La llegada real del archivo debe comprobarse; una ruta o hash no lo transporta entre máquinas.

Para A, proponer un cambio separado y revisado al constructor de comandos: manifiesto por tarea de servidores/tools permitidos, parámetros explícitos `-c` sin valores secretos, timeouts y fallo cerrado. Ejemplo conceptual no ejecutado: `-c 'mcp_servers.github.url="https://api.githubcopilot.com/mcp/readonly"'` y `-c 'mcp_servers.github.bearer_token_env_var="GITHUB_READ_TOKEN"'`; requiere inyección segura externa y allowlist concreta de herramientas después de cotejar catálogo. La ayuda acepta overrides TOML; su funcionamiento MCP bajo ignore, autenticación y herencia de entorno **no están probados**. No quitar ignore ni trasladar todo el config global para hacerlo funcionar.

Para B, el coordinador ejecutaría la prelectura antes del hijo y le entregaría únicamente salida validada; preferible a dar token amplio al proceso. Revisores no deben recibir secretos ni lecturas vivas: revisan entrega y recibos con su sandbox de sólo lectura. Lanzar y reanudar deben conservar el mismo manifiesto aprobado o bloquear ante cambio; no heredar conectores del coordinador por inferencia.

No se modificó harness, configuración global, cuentas, scopes ni secretos. Las pruebas de fallos y de integración están especificadas en [PRUEBAS](PRUEBAS.md), todas sin ejecutar contra servicios.
