## Coordinación de tareas sin saturar el contexto

GitHub conserva el registro único y los entregables. Cada tarea tiene objetivo, alcance de escritura, entradas, aceptación, ejecutor, modelo/esfuerzo, presupuesto y próximo paso. El coordinador recupera esa ficha, no todo el historial. Cada ejecutora usa una rama y worktree propios; su revisor recibe el commit y el criterio. El tablero muestra trabajo, bloqueo y revisión como estados distintos.

Se libera un cupo al terminar el proceso, pero una tarea no está terminada por eso: necesita entrega remota, revisión buena, aceptación e integración comprobada en origin/master. Si falta acceso o una decisión, pasa a en_espera con causa y condición de salida, conservando SID/archivos/rama; se puede continuar una tarea independiente. Una corrección retoma el mismo SID cuando corresponde y revisa el nuevo commit.

Esta noche el coordinador despacha manualmente el lote aprobado con el harness. El scheduler de carriles sigue pendiente; el piloto aprobado sólo incluye Workshop/Investigación, tres cupos globales con revisores y máximo un hijo. No ampliar ese sí a Platform ni automatizaciones de producción.

## Criterio para abrir otro frente

Abrir sólo si hay un resultado útil definido, rutas y recursos libres, autorización aplicable y cuota. Priorizar cerrar revisiones antes de acumular borradores. Parar nuevos despachos al55% de cuota semanal usada en este lote o cuando una dependencia excluyente requiera a Sergio. No gastar presupuesto repitiendo el mismo fallo sin cambiar una condición comprobable.
