**4. Cómo funciona un encargo y cómo continúa**

Cada encargo define objetivo, responsable, entradas, entregable, permisos y aceptación. Selecciona una directora y apoyos pertinentes; enlazarlos no demuestra que sus cuerpos se hayan leído.

El ciclo es observar → investigar una duda → priorizar → ejecutar lo autorizado → comprobar → medir → corregir. Los dos ciclos de corrección eran una propuesta inicial, no reintentos ilimitados.

El **JSON es autoridad de estado y briefing**; el Markdown es una proyección comprobable. Una tarea privada queda en `operacion/`; una compartible exige contenido saneado y evidencia versionada. No se exportan automáticamente datos privados.

El ejecutor declara comprobación y entrega `para_revision`. El revisor contrasta aceptación y evidencia y registra `aceptar`; terminar no equivale a aceptar. Revisiones esperadas, hashes y reservas previenen ciertas inconsistencias, pero no autentican personas ni coordinan todos los clones. Se conserva evidencia anterior y se rechaza corrupción o revisión obsoleta.

La continuidad **A→Git→B** transporta registro, briefing, decisiones y evidencia publicados: B recupera ID, repositorio y commit y continúa sobre la revisión correcta. No migra chats completos, historial, VMs, secretos ni tokens.

`ESTADO.fuente.txt` atribuye aprobación técnica a una prueba real A→Git→B. También diferencia 54/54 pruebas de una versión y 74 aprobadas más una omisión Windows en una evaluación posterior. Eso no valida automáticamente el VPS actual. El anuncio nativo Cloud, la compacción y el uso real de iPhone seguían sin acreditarse.
